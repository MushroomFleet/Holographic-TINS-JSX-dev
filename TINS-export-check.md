## What TINS Requires

The specification defines a TINS README as **the sole source of information for an LLM to regenerate functional software**. The core idea: distribute only the README, and any capable LLM can produce a working implementation from it.

### Required Sections (from specification.md)

| # | Section | Required? | Purpose |
|---|---------|-----------|---------|
| 1 | **Project Title** (H1) | Required | First line, level 1 heading |
| 2 | **Description** | Required | Purpose and key features, 1-3 paragraphs |
| 3 | **Functionality** | Required | Core features, UI, behavior specs |
| 4 | **Technical Implementation** | Required | Architecture, data structures, algorithms |
| 5 | Style Guide | Recommended | Visual design specs |
| 6 | Testing Scenarios | Recommended | Test cases |
| 7 | Accessibility Requirements | Recommended | A11y specs |
| 8 | Performance Goals | Recommended | Metrics and targets |
| 9 | Extended Features | Recommended | Optional enhancements |

### Validation Checklist (from skill.md)

- [ ] Has clear project title and description
- [ ] Details all core features comprehensively
- [ ] Describes user interface and interactions
- [ ] Specifies technical implementation approach
- [ ] Includes data models and structures
- [ ] Addresses edge cases and error handling
- [ ] Provides examples where appropriate
- [ ] Uses consistent terminology throughout
- [ ] Has no contradictions or ambiguities
- [ ] Includes diagrams for complex flows
- [ ] Specifies accessibility requirements
- [ ] Defines performance expectations

## Gap Analysis

### FATAL: The export is NOT a TINS README

The fundamental problem is a **category mismatch**. A TINS README is a specification document from which an LLM can regenerate the software. Our export is a **build log / provenance report** — it documents how the app was built but cannot be used to rebuild it.

| TINS Purpose | Our Export Purpose |
|---|---|
| Sole source for LLM code generation | Historical record of a conversation |
| Replaces source code distribution | Accompanies source code (the HTML file) |
| Self-contained specification | References external output file |
| Enables regeneration by any LLM | Documents one specific generation session |

## Recommendation

The current export should be **renamed** from "TINS README" to something like "Build Report" or "Provenance Log" — it has value as a record of the conversation, but it is not TINS-compliant.

To produce an actual TINS README, the export would need to:

1. **Analyze the generated HTML** — Read the final `.html` file and extract what the app does (UI components, interactions, features, data structures)
2. **Generate a specification from the implementation** — Use Claude to reverse-engineer a TINS-compliant README from the working HTML, structured with all required sections
3. **Include the full TINS heading hierarchy** — Description, Functionality (Core Features, User Interface, Behavior Specs), Technical Implementation (Architecture, Data Model, Algorithms)
4. **Add TINS metadata** — Version tag, platform tag, complexity tag
5. **Validate the output** — Check that the generated README, if given to a fresh LLM, would produce equivalent software

The simplest approach: after the user clicks "TINS export", send the final HTML file content to Claude with a prompt like: *"Analyze this HTML application and generate a TINS-compliant README specification that would allow an LLM to regenerate an equivalent application."* Then save Claude's output.
